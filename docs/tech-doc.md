## 摘要

课表规划是一个面向大学生的**学习规划工具**：拍下课程表照片，说一个目标（例如「期末高数考到 80 分」），它会先算出你的课表还剩下多少空档，再把目标拆成一组可执行的知识点，给出三套节奏不同的方案（分散式 / 集中式 / 冲刺式），由你选定之后，把知识点排进具体时段，并在到点时提醒你。

本文档重点回答一个问题：**这个产品与"直接把需求告诉通用 AI"有什么区别。**

答案是三层分工：

| 层 | 负责什么 | 为什么不能换人做 |
|---|---|---|
| **程序** | 时间换算、区间相交、空档计算、可行性判定、数据校验 | 这些有唯一正确答案，模型会算错 |
| **模型** | 看图读写、理解语义、生成权衡与表达 | 这些没有唯一答案，程序写不出来 |
| **用户** | 选方案、改知识点、确认识别结果 | 决定权必须留在人手里 |

全文共 8 章：选题定位、产品设计、架构分工、意图控制的四个实例、实测数据、工程质量、已知局限、可复现性。

# 第 1 章 选题与定位

## 1.1 这个题目是怎么定下来的

本项目是第二次提交。第一次的作品是一个「代码学习助手」，预指导阶段得分 **63 分**，评委给出的评语只有一句：

> 这个产品和直接问豆包 / DeepSeek，或者用 Claude Code 比，有什么区别呢？

这句评语指向的不是「功能不够多」，而是**定位没有说清**。一个「能聊天的界面 + 几个预设提示词」在 2026 年已经不能构成产品差异。

因此第二次立项时，选题标准只有一条：**有没有一件事，是通用 AI 结构上做不到的。**

## 1.2 找到的那个"结构上做不到"

思考过程落在一个很具体的问题上：

```
学生说：「我想期末高数考到 80 分，帮我排个计划。」
通用 AI 会给出一段建议——通常是"每天复习 1 小时""注意错题整理"这类。
但它不知道：这名学生周三第 1-8 节都有课，周四下午是空的。
```

**通用 AI 缺少的不是语言能力，而是两样东西：**

1. **你的真实时间约束**（课表）。它没有这份数据，只能靠你口述，而口述必然不完整。
2. **校验能力**。它给出的日程可能和你上课时间冲突，但它无法发现——**它连"冲突"这件事都无法计算**。

这两样恰好是**程序最擅长**的：时间区间是否相交是纯数学问题，有唯一正确答案。

## 1.3 产品的定位一句话

> **AI 负责"怎么排"，程序负责"排不排得下"，用户负责"用哪个方案"。**

## 1.4 目标用户与非目标

**目标用户**：有明确课表、有学习目标、但不会自己做计划的大学生（本项目作者本人就是）。

**非目标**：

- 不是给开发者用的任务管理工具（不做番茄钟、不做 GTD 方法论）；
- 不是团队协作工具（不做多人共享、不做权限）；
- 不做教务系统代登录（详见第 7 章局限 3）。

# 第 2 章 产品设计：五段式规划链

## 2.1 完整链路

```
① 导入课表      拍照 / 选图 → 视觉模型识别 → 可编辑的校对表 → 落到周视图
                              （程序校验 + 可疑行标黄 + 用户确认）

② 说出目标      底部输入框说话；程序先判断意图：
                   · 含具体时间点（"周三晚上7点"）→ 直接加一条事件
                   · 目标型语句（"我要学高数"）→ 弹出目标澄清卡
                        （每周可投入几小时 / 截止日期）

③ 知识点大纲    目标 → 8-20 个可执行知识点（含章节 / 难度 / 预估时长）
                   · 程序把总时长加出来 → 「一共 29.5 小时」
                   · 可勾选、可改名、可改时长、可删、可加
                   · 也可粘贴教材目录，要求模型"只按目录拆，不许自己加"

④ 可行性 + 方案  程序判断「你承诺每周 H 小时，课表装得下吗」
                   → AI 给三档节奏方案（分散 / 集中 / 冲刺），各带优缺点与风险
                   → 模型只写文字，所有数字由程序算

⑤ 落地与提醒    按选定方案 + 选中知识点生成任务（标题就是知识点名）
                   → 预览 → 逐条剔除或全部接受 → 到点提醒
```

## 2.2 为什么知识点必须放在"方案"之前

这是设计过程中改过一次的顺序。

**原来的顺序**：目标 → 方案 → 日程。

问题：可行性判断里的「达成目标需要多少小时」只能让模型估。实测它把「期末高数 80 分」估成 **80 小时**，而用户填的是每周 10 小时、距截止 5.5 周（可用 55 小时），于是被判定为「不可行」——**一个本可行的目标被误判**。

**改成**：目标 → 知识点 → 方案 → 日程。

知识点清单给出的是客观量：15 个知识点、合计 1770 分钟 = **29.5 小时**。这个数字由程序从清单里加出来，不需要模型估。于是可行性变成一次纯算术比较：

```
需求 29.5 小时  vs  可用 10 × 5.5 = 55 小时  →  可行，余量 25.5 小时
```

**一举两得**：可行性有了依据；日程标题也从「复习高数」变成了「隐函数求导」。

## 2.3 三档方案不是模型自由发挥

方案的三档节奏是**预先定义**的，模型只负责把取舍讲清楚：

| 方案 | 策略标识 | 节奏（由程序算） | 优点 | 代价 |
|---|---|---|---|---|
| 分散式 | `daily` | 每周 7 次，每次 `round15(H×60/7)` 分钟 | 记忆最牢、易成习惯 | 要求每天坚持 |
| 集中式 | `weekly` | 每周 3 次，每次 `round15(H×60/3)` 分钟 | 单次深入、适合攻坚 | 间隔长易遗忘 |
| 冲刺式 | `sprint` | 每周 4 次，每次 `round15(H×60/4)` 分钟 | 前期压力小 | 后期风险高 |

其中 `H` 是用户填的「每周可投入小时数」，`round15` 是取整到 15 分钟。

**这样三个方案的每周投入必然等于用户承诺的 H，不会出现"填 10 小时却排了 14 小时"。**

## 2.4 界面结构

| 界面 | 内容 |
|---|---|
| **日程（主界面）** | 0–24 小时 × 7 天网格；事件按类型着色；空闲时段淡绿底纹；当前时间红线；点空白格弹轻量气泡 |
| **周 / 月 / 年目标** | 三层目标列表，带嵌套校验（「未拆解」「未归属」）与关联时长汇总 |
| **目标澄清卡** | 输入"我要学高数"后弹出：每周几小时 + 截止日期 + 「让 AI 给方案」/「只加一条事件」 |
| **知识点大纲面板** | 逐条勾选/编辑；显示来源（AI 生成 / 你提供的目录）；标注"可能与本校教学进度不同" |
| **方案对比面板** | 可行性条（可行/紧张/不可行）+ 三张方案卡（思路/节奏/优点/代价/风险）+ 推荐 |
| **规划预览** | 生成的事件列表，可逐条剔除；显示"被自动调整 N 条""因放不下忽略 N 条" |
| **校对表** | 识别结果逐行可改；可疑行整行标黄；作息时间可编辑；追加导入 / 覆盖导入 |

**五个接口都遵循同一条边界**：模型碰不到"绝对时间"和"数字"。

## 3.4 确定性工作的四个落点

| 落点 | 具体做什么 | 为什么必须是程序 |
|---|---|---|
| **时间换算** | `date = weekStart + (day-1)`；`startMin = startHour*60 + startMinute` | 模型实测把「本周三晚上 7 点」算成「周一 21:00 到次日 6:00」 |
| **区间相交** | 同一天两段时间是否重叠 | 纯数学，有唯一答案 |
| **空档计算** | 08:00–23:00 减去全部事件占用，丢弃 <30 分钟碎片 | 必须与真实课表严格一致 |
| **可行性判定** | `H > 本周空档小时` → 不可行；`需求 > 可用×0.8` → 紧张 | 不能让模型"估"需要多少小时 |

# 第 4 章 意图控制的四个实例

本章是全文的核心。**"意图控制"在本项目里不是一句口号，而是四次具体的"把某件事从模型手里拿回来"**，每一次都有实测数据支撑。

## 4.1 实例一：日期算术

**最初的契约**：模型直接返回绝对时间。

```
输入「每周三晚上7点到9点复习高数」
模型返回：date=2026-11-10（周一，且已过去）、startMin=1260（21:00）、endMin=1800（30:00）
正确答案：2026-11-11（周三）19:00-21:00
```

三处全错，而且 `endMin = 1800 > 1440` 会被前端校验直接丢弃——**用户说完话，界面什么都不会发生，也没有任何提示**。

**第一次修正**：模型只说语义，程序算绝对时间。

```
{ "day": 3, "startHour": 19, "startMinute": 0, "durationMin": 120 }
  → 程序：date = weekStart + 2 天；startMin = 1140；endMin = 1260
```

**第二次修正**：绝对日期好了，相对日期还错。

```
输入「明天下午3点开会」→ 返回 2026-11-13（周五），应为 2026-11-12（周四）
根因：相对日期仍要模型换算成"本周几"，而它又算错
修正：契约增加 dayOffset（0=今天 1=明天），相对日期完全不经模型换算
```

**最终契约**：

| 用户说法 | 模型输出 | 程序计算 |
|---|---|---|
| 「周三晚上 7 点」 | `day = 3` | `date = weekStart + 2` |
| 「明天下午 3 点」 | `dayOffset = 1` | `date = today + 1` |
| 「下周三」（本次已过） | `day = 3` | `date += 7`，回复补「已安排到下周」 |

**模型一次绝对日期都不输出。**

## 4.2 实例二：方案的数字

**第一次实测**（目标：期末高数 80 分 / 每周 10 小时 / 5.5 周）：

```
可行性：不可行（需要 80 小时，可用 55 小时）
   ↑ 模型自己估"学高数要 80 小时"，没有依据
方案 A：每周 7 次 × 120 分钟 = 14 小时/周
   ↑ 用户填 10 小时/周，超了 40%
```

**第二个用例**（每周 30 小时）：

```
方案 A：每周 7 次 × 30 分钟 = 3.5 小时/周
   ↑ 用户填 30 小时，只给了 11%
```

**修正**：`sessionsPerWeek`、`avgSessionMin`、`totalHours`、`requiredHours`、`supplyHours`、`gapHours` **全部由程序计算**，并且 Prompt 里明确禁止模型输出这些字段。服务端按方案 id 合并：数字用程序的，文字（名称/思路/优缺点/风险）用模型的。

**修正后实测**：

```
方案 A：每周 7 次 × 90 分 = 10.5 h/周   偏差 5%
方案 B：每周 3 次 × 200 分 = 10.0 h/周  偏差 0%
方案 C：每周 4 次 × 150 分 = 10.0 h/周  偏差 0%
```

## 4.3 实例三：可行性判断的定义

**改之前**：让模型估「达成这个目标需要多少小时」。

问题在于：这个数**没人知道**，模型也只是猜。实测把「每周 10 小时 / 5.5 周」（可用 55 小时）的目标估成需要 80 小时，判为不可行。

**改之后**：换成一个程序能精确回答的问题。

```
你承诺每周投入 H 小时，你的课表容得下吗？

weeklyCapacity = 本周空档小时（程序算）
demandHours    = H × 剩余周数
capacityHours  = weeklyCapacity × 剩余周数

H > weeklyCapacity              → 不可行
demandHours > capacityHours×0.8 → 紧张
其余                             → 可行
```

而 `demandHours` 的分子（知识点的总时长）来自第 2.2 节的知识点清单，同样由程序求和。

**这样整条可行性判断里没有任何一个数字来自模型。**

## 4.4 实例四：识别结果的坐标

课表识别的数据链路改了**五次契约**，每次都因为实测数字被否决：

| 版本 | 契约 | 星期 | 节次跨度 | 平均时间误差 |
|---|---|---|---|---|
| 1 | 模型自己判断 `day`/`startSlot` | 2/10 | 1/10 | — |
| 2 | 网格 `columns/rows/cells` | 7/10 | 0/10 | — |
| 3 | 课程块 `blocks` | 7/10 | 0/10 | 40.5 分钟 |
| 4 | 比例坐标 + `Math.round` | 7/10 | 0/10 | 40.5 分钟 |
| 4' | 比例坐标 + `Math.floor`（数学修正） | **5/10** | 0/10 | 53 分钟 |
| **5** | **`colIndex` 优先 + 程序兜底 + 标黄** | **9/10** | **8/10** | **11.5 分钟** |

**版本 4' 是这个项目最重要的一次发现**：

第 k 列的中心比例是 `(k-0.5)/colCount`，乘回 `colCount` 得 `k-0.5`，`Math.round(k-0.5)` 进位成 `k`，再 +1 就是 `k+1`——**前 6 列整体右移，第 6、7 列被夹成同一列**。

把 `Math.round` 改成 `Math.floor` 是**数学上正确**的修正。但实测星期准确率从 7/10 **掉到 5/10**。

原因：模型给出的 `leftRatio/rightRatio` **系统性偏左约半列，且只偏一部分块**；`round` 版本那次"多 +1"恰好补偿了这个偏差。

> **结论：这不是公式错，是模型的输入有系统偏差。靠修公式去补偿，只是碰运气。**

**最终方案**放弃比例，改回"模型判断 + 程序兜底"：

1. 模型给 `colIndex`（它判断第几列）；`leftRatio` 只用于交叉校验，两者相差 ≥2 列时标 `suspect`；
2. 节次若 `rowEnd === rowStart`（模型读不出块高），程序默认 `+1` 节并标 `suspect`；
3. 可疑行在校对表里整行标黄，交给用户确认。

**这一版把节次跨度从 0/10 直接提到 8/10**——因为大学课程多为两节连上，默认值本身就大概率正确，而错的那两行会被标黄。

## 4.5 四次实例的共同点

| 实例 | 从模型手里拿走的东西 | 拿走之后谁做 |
|---|---|---|
| 日期算术 | 绝对日期与分钟数 | 程序用 `day`/`dayOffset` 换算 |
| 方案数字 | 每周次数、单次时长、总时长 | 程序用 `H` 与 `round15` 计算 |
| 可行性 | "需要多少小时" | 程序用知识点总时长与空档相乘比较 |
| 识别坐标 | 行列映射 | 程序用 `colIndex` + 兜底规则 + 可疑标记 |

**一句话概括本项目对"意图控制"的理解**：

> 意图控制不是"把提示词写得更好"，而是**在动手之前就把每一件事的责任边界划清楚**：
> 哪些必须由程序算（因为错了就是错了），哪些交给模型（因为没有唯一答案），
> 哪些必须由用户决定（因为只有他知道自己要什么）。

# 第 6 章 工程质量与安全边界

## 6.1 安全设计

| 措施 | 实现 | 位置 |
|---|---|---|
| **密钥只在服务端** | 五个接口均从 `process.env.ZHIPU_API_KEY` 读取，客户端从不接收 | 全部 route |
| **错误出口脱敏** | 返回给浏览器的错误文本若含密钥，替换为 `***` | `lib/llm.ts` `desensitize()` |
| **滑动窗口限流** | 按客户端 IP，60 秒窗口 | `lib/rateLimit.ts` `checkRateLimit()` |
| **请求体体积上限** | plan: 文本 500 字；goal/advise: 8 KB；syllabus: 16 KB；recognize: base64 8 MB | 各 route 常量 |
| **上游重定向拒绝** | `redirect: "manual"`，遇 3xx 直接判失败（防白名单被重定向绕过） | `recognize/route.ts` |
| **不可信输入校验** | 模型返回的每一项都重新校验并夹取范围，不合法项丢弃并计数 | 各 `lib/*` 纯函数 |
| **零结果不静默** | 识别不出课程时返回 422 而非 200 + 空数组 | `recognize/route.ts` |

**关于限流数值的说明**：初版设 5 次/分钟，实测连发三条指令就会被 429 挡住（对单人使用过紧），后放宽到 10 次/分钟。**这是被真实使用体验修正的参数，不是拍脑袋定的。**

## 6.2 已知的工程权衡

| 权衡 | 选择 | 理由 |
|---|---|---|
| 依赖数量 | 只保留 3 个生产依赖 | 时间紧，引入组件库的样式覆盖成本高于手写 |
| 数据存储 | localStorage | 无账号体系，避免登录与数据库；代价是换设备不同步（见局限 2） |
| 状态管理 | 集中在 `page.tsx`（1384 行） | 12 个以上状态互相关联，拆分会增加跨模块传参成本；**这是本项目最大的技术债** |
| 通知 | 软件内卡片为主，系统通知可选 | 系统通知需要用户授权，未授权时演示会"看起来没实现" |

## 6.3 评测工具链

`eval/` 目录是本项目"让准确率可判断"的基础设施：

| 文件 | 作用 |
|---|---|
| `run.mjs` | 调用识别接口，把完整响应（含耗时、HTTP 状态）原样落盘到 `cases/` |
| `compare.mjs` | 与标准答案比对，输出四项指标 + 逐门明细，结果写入 `results/` |
| `timetable-groundtruth.json` | 真实课表标准答案（10 门课的星期/节次/地点/作息） |

**指标口径**（写在文档里避免漂移）：

1. **课程名匹配**：去掉括号序号与空白后按"完全相等或互相包含"匹配，统计命中/漏报/多报；
2. **星期准确率**：在**命中课程**里算，漏报不拉低分母；
3. **节次跨度准确率**：`startSlot` 与 `endSlot` 同时相同才算对；
4. **平均时间误差**：用识别返回的作息把课换成分钟，与标准答案比 `|startMin 差|` 与 `|endMin 差|` 的平均。

**为什么拆成四项而不是一个"整体准确率"**：星期、节次、时间三类错误互相独立，合成一个数会让"星期对但节次错"与"全错"看起来一样。

# 第 7 章 已知局限

如实记录，不隐藏。

**1. 提醒需要软件保持打开。**
浏览器没有系统级后台定时权限，页面关闭后不会响铃。真正的系统闹钟需要桌面端常驻进程或手机原生 App。

**2. 数据只存在本机浏览器。**
清除浏览器数据会丢失；换设备不同步。这是"无账号体系"的代价。

**3. 不做教务系统代登录。**
曾评估过"输入教务系统账号密码自动导入课表"，最终否决，原因有三：其一，需要收集学生的教务系统密码，属于高敏感凭据，泄漏后果严重；其二，各校登录流程不同（验证码、RSA 加密、统一认证），短期无法覆盖；其三，多数教务系统用户协议禁止第三方程序代登录。**本项目选择"拍照识别 + 人工校对"这条低风险路径。**

**4. 识别准确率不是 100%。**
实测星期 90%、节次跨度 80%。剩余错误集中在"跨 4 节的课被读成 2 节"。因此产品设计上**不允许识别结果直接写入日程**，必须经过校对表。

**5. 知识点大纲可能与本校教学进度不符。**
默认按主流教材生成，界面上明确标注「AI 按主流教材生成，可能与本校教学进度不同，请核对」。提供两条兜底：粘贴教材目录（要求模型只按目录拆分）、手动增删改。

**6. 课表只支持单周。**
导入时按当前周生成实例（可选生成 4 周），不做单双周、不做调课周。

**7. 限流是尽力而为。**
计数器存在进程内存中，本地与单实例有效；多实例部署时各算各的，冷启动会重置。严格的全局限流需要外部存储（如 Redis）。

**8. 状态集中在单个组件。**
`page.tsx` 1384 行、12 个以上 `useState`。功能可用，但后续维护成本高。这是本轮"先跑通再重构"的取舍，已列入未来工作。

**9. 开发依赖存在 7 个 moderate 告警。**
均在 `@typescript-eslint → minimatch`（lint 工具链），生产依赖为 0 漏洞。升级需破坏现有 lint 配置，本轮记录不修。

# 附录 C · 术语

| 术语 | 在本项目里的含义 |
|---|---|
| **空档（free slot）** | 08:00–23:00 减去全部事件占用后的连续空闲区间，短于 30 分钟的碎片丢弃 |
| **课程块（block）** | 视觉模型输出的一个课程矩形：名称、所在列、起止行、地点、周次 |
| **可疑行（suspect）** | 识别结果中"模型判断与几何比例矛盾"或"读不出跨节高度"的课程，校对表整行标黄 |
| **知识点（knowledge point）** | 一次 30–240 分钟能学完的内容单元，是"目标"与"日程"之间的中间层 |
| **方案（option）** | 三档节奏之一（daily / weekly / sprint），只描述"怎么分配时间"，不包含具体事件 |
| **可行性（feasibility）** | 「你承诺每周投入 H 小时，课表容得下吗」的程序判定结果：可行 / 紧张 / 不可行 |
| **质检工具链（eval）** | `run.mjs` 抓取识别结果 + `compare.mjs` 与标准答案比对，输出四项指标 |
