# 03 · 把日期算术从模型手里拿回来

> **一句话**：让模型算"本周三是几号"，它连错两次；最后改成**模型只说周几和几点，日期由程序算**。
> **完整对话**：`raw/对话导出-2-全部开发轮次.md` 第 12、13 轮

---

## 一、第一次实测：一句话被算成了"昨天 21 点到第二天早上 6 点"

`/api/plan` 的初版让模型直接返回**绝对时间**：

```json
{ "actions": [{ "op": "add",
  "event": { "date": "2026-11-11", "startMin": 1140, "endMin": 1260, "title": "复习高数" } }] }
```

实测输入「每周三晚上 7 点到 9 点复习高数」，模型返回：

```
date = 2026-11-10（周一，而且已经过去）
startMin = 1260（21:00）
endMin = 1800（30:00 —— 超过一天的 1440 分钟）
```

**正确答案是 2026-11-11（周三）19:00-21:00。三处全错。**

更糟的是 `endMin = 1800 > 1440`，会被前端的校验**直接丢弃**：

```
用户说了一句话 → 界面上什么都没有发生 → 也没有任何解释
```

---

## 二、第一次修正：模型只说语义，程序算时间

### 我的提问（原文摘录）

```
修复 AI 落事件的日期与时间换算错误。

问题（实测）：
输入「每周三晚上7点到9点复习高数」，模型返回
date=2026-11-10（周一，且已过去）、startMin=1260（21:00）、endMin=1800（30:00）
正确答案应为 2026-11-11（周三）19:00-21:00。
且 endMin=1800 超出 1440 会被前端校验丢弃，用户看不到任何反馈。

根因：把日期算术交给了模型。改成模型只输出语义，程序算绝对时间。

要做：
1. 提示词改为要求返回：
{ "day": number, "startHour": number, "startMinute": number, "durationMin": number, ... }
   明确：不要说日期、不要说分钟数，只给「本周几 / 几点 / 多久」；
   遇到「晚上7点」要换算成 startHour=19；遇到「到9点」要算 durationMin=120。
2. 服务端完成换算并校验：
   date = weekStart + (day-1) 天
   startMin = startHour*60 + startMinute
   endMin = startMin + durationMin
3. 前端 executePlan 简化：服务端已换算并校验，前端只按 op 执行
```

### 结果

```
「每周三晚上7点到9点复习高数」-> 2026-11-11 19:00-21:00  ✓ 完全正确
```

## 三、第二次实测：绝对日期修好了，相对日期还错

继续测另外两句，发现新问题：

| 输入 | 返回 | 应该 |
|---|---|---|
| 明天下午3点开会 | **2026-11-13**（周五） | 2026-11-12（周四） |
| 周六上午9点到11点写Java作业 | （被自己的限流 429 挡了） | 2026-11-14 |

**今天是 11-11（周三），"明天"是 11-12。模型把周四算成了周五。**

同时暴露第二个问题：**限流 5 次/分钟太紧** —— 连发三条指令就撞 429。

### 我的提问（原文摘录）

```
修复相对日期换算错误，并放宽限流。

问题（实测）:
今天 2026-11-11（周三），weekStart=2026-11-09。
输入「明天下午3点开会」返回 date=2026-11-13（周五），应为 2026-11-12（周四）。
根因: 相对日期仍由模型换算成「本周几」，模型算错。

修改:
【一】契约增加 dayOffset 字段
  "day": number|null,        // 绝对周几 1-7
  "dayOffset": number|null,  // 相对今天：0=今天 1=明天 2=后天
  提示词明确：
  - 「明天/后天/大后天」-> 用 dayOffset（1/2/3），day 给 null
  - 「周三/星期五」-> 用 day（1-7），dayOffset 给 null
  - 两者都有时 dayOffset 优先
  - 仍然不许输出绝对日期
【二】服务端换算顺序
  - dayOffset 在 0..6 -> date = today + dayOffset 天
  - 否则 day 在 1..7 -> date = weekStart + (day-1) 天
  - 用 day 分支算出的 date 若早于 today -> 加 7 天，并补一句「已安排到下周X」
【三】限流从 5 次/分 放宽到 10 次/分
```

### 结果

```
「明天下午3点开会」 -> 2026-11-12 15:00-16:00  ✓
连发 6 条指令不再出现 429
```

## 四、最终契约（三种日期语义，都由程序换算）

| 用户说法 | 模型输出 | 程序计算 |
|---|---|---|
| 「周三晚上7点」 | `day = 3` | `date = weekStart + 2 天` |
| 「明天下午3点」 | `dayOffset = 1` | `date = today + 1 天` |
| 「下周三」 | `day = 3`（算出的日期已过） | `date += 7 天`，reply 补「已安排到下周」 |

**模型一次绝对日期都不输出。**

---

## 五、人工干预小结

1. **第一次判断**：把"日期算术"从模型手里拿走，只让它做语义解析（周几、几点、多久）。
2. **第二次判断**：发现"相对日期"仍要模型换算成"周几"，而它又算错 ——
   于是**再加一条 `dayOffset` 通道**，让"明天"这类表达完全不经模型换算。
3. **顺手修限流**：5 次/分是自己试出来的，连发三条就被挡，对单人使用过紧。

---

## 六、这条链的通用结论

> **凡是"有唯一正确答案"的计算，都不该让模型做。**
>
> 日期算术、分钟换算、区间相交 —— 这些错了就是错了，没有"语言风格"的余地。
> 模型的强项是**理解"晚上 7 点"指的是 19 点**，弱项是**算出 11 月 12 日是周几**。
>
> 本项目由此形成一条固定分工：
> **模型输出语义（周几 / 几点 / 多久），程序输出坐标（日期 / 分钟数 / 区间）。**
