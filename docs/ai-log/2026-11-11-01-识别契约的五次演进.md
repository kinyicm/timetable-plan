# 01 · 课表识别契约的五次演进

> **一句话**：同一个功能改了五次契约，每一次都是被**实测数字**逼出来的，而不是"感觉不准就再试一次"。
> **最终结果**：课程名 10/10、地点 10/10、星期 9/10、节次跨度 8/10、平均时间误差 11.5 分钟。
> **完整对话**：`raw/对话导出-2-全部开发轮次.md` 第 22、24、25、27、32、35、38 轮

---

## 一、起点与目标

课表导入的数据链路是：

```
课表照片 → GLM-4V 读图 → 结构化 JSON → 程序规整 → 落到周视图
```

设计原则一开始就定好了：**模型只负责"看图读字"，行列坐标由程序算**。
但"怎么让模型把看到的东西交出来"这件事，改了五次契约。

**为什么要反复改**：因为判断标准不是"看起来对不对"，而是 `eval/compare.mjs` 给出的四个数字：
课程名匹配、星期准确率、节次跨度准确率、平均时间误差。

---

## 二、第 1 次：让模型自己判断星期与节次（失败）

### 我的提问（原文摘录）

```
请识别这张「课程表」图片，严格只输出一个 JSON 对象……
{
  "name": "...", "day": number, "startSlot": number, "endSlot": number, ...
}
- day 表示星期几：1=周一……
- startSlot / endSlot 表示第几节课，从 1 开始
```

### AI 产出

`/api/recognize` 直接返回 `courses[]`，每条带 `day/startSlot/endSlot`；
程序侧只做取值范围夹取。

### 实测（真实课表，10 门）

```
星期正确 2/10   节次正确 1/10
模型返回的 day 全部是 1，startSlot 按 1,3,5,6,7,8,9,10,11,11 递增
```

### 诊断

**模型把二维课表当成"一列从上往下"读了**，完全没有"列 = 星期"的概念。
这不是随机误差，是结构性的理解失败。

### 我的决定

把"判断星期"从模型手里拿走，改成**让模型抄格子、程序算坐标**。

---

## 三、第 2 次：网格契约 `columns / rows / cells`（部分成功，但埋了雷）

### 我的提问（原文摘录）

```
改 /api/recognize 的输出契约：让模型抄格子，坐标由程序算。
……
{
  "columns": [{ "index": number, "label": string }],
  "rows": [{ "slot": number, "cells": string[] }]
}
- columns 按图片从左到右列出表头文字……
- cells 的长度必须等于 columns 的长度，一一对应；
- 不要做任何"这门课属于星期几"的判断——那是程序的事。
```

### AI 产出

新增 `lib/gridToCourses.ts`：按列下标映射星期、按行下标映射节次，
并把纵向相邻且文字相同的格子合并成一门课。

### 实测

```
课程名 10/10 ｜ 地点 10/10 ｜ 星期 7/10 ｜ 节次跨度 0/10
```

### 第一处致命问题（我发现的）

**看代码时发现**：模型返回的 `cells` 长度是 5、2、1、1…，与 `columns` 的 7 项不一致；
而 `gridToCourses` 的校验是"长度不等就整行丢弃"。

**实测复现**：`droppedCount = 10`、`courses = []`，但 HTTP 仍 200、`ok = true`。

> **用户看到的是空校对表格，完全不知道识别失败。**
> 这是最糟的失败模式 —— 不是报错，而是"静默清零"。

### 第二处问题（我发现的）

即使长度对齐，节次跨度仍然是 0/10。
原因：WakeUp 这类课表 App 的合并单元格**只在块中央显示一次文字**，
其余行是空的；靠"相邻行文字相同"去合并，永远合不上。

## 四、第 3 次：课程块契约 `blocks` + 零结果返 422

### 我的提问（原文摘录）

```
修复 /api/recognize 的一处严重回归：实测返回 0 门课，但接口仍返回 ok=true。
……
【一】契约改为「课程块列表」，不再要求模型输出对齐的二维数组
{
  "blocks": [{
    "name": string,
    "col": number,       // 第几列，1=周一 … 7=周日
    "rowStart": number,
    "rowEnd": number,
    "location": string,
    "weeks": string
  }]
}
【三】绝不再静默清零
- 若 courses.length === 0：返回 HTTP 422，
  body { ok:false, error:"未能从图片中识别出任何课程，请换一张更清晰的截图，或改用手动录入" }
```

### AI 产出

新增 `lib/blocksToCourses.ts`，删除 `gridToCourses.ts`；
零结果返回 422；`invalidCount` 透给前端提示。

### 实测

```
课程名 10/10 ｜ 地点 10/10 ｜ 星期 7/10 ｜ 节次跨度 0/10 ｜ 平均时间误差 40.5 分钟
```

星期从 2/10 提到 7/10（**印证了"模型判断列"比"模型估比例"更符合它的能力**），
但节次跨度仍是 0/10：每门课都报成 1 节（`5-5`、`1-1`）。

## 五、第 4 次：比例坐标 `leftRatio / topRatio`（数学上对，实测反而更差）

### 我的提问（原文摘录）

```
把 /api/recognize 的 blocks 契约从「模型自己数行列」改成「模型只报相对位置」。
……
{
  "slotCount": number, "colCount": number,
  "blocks": [{
    "name": string,
    "leftRatio": number, "rightRatio": number,
    "topRatio": number, "bottomRatio": number,
    ...
  }]
}
【二】程序侧换算
- col      = clamp(round(((leftRatio + rightRatio) / 2) * colCount) + 1, 1, colCount)
- startSlot = clamp(round(topRatio * slotCount) + 1, 1, slotCount)
- endSlot   = clamp(round(bottomRatio * slotCount), 1, slotCount)
```

### 实测

```
星期 7/10 ｜ 节次跨度 0/10 ｜ 平均时间误差 40.5 分钟
```

### 第三处问题（审阅时发现的，可以数学证明）

第 k 列的中心比例是 `(k-0.5)/colCount`，乘回 `colCount` 得 `k-0.5`，
`Math.round(k-0.5)` 进位成 `k`，再 `+1` 就是 `k+1`。

**按 7 列实算**：

| 真值列 | 计算值 | round+1 | 结果 |
|---|---|---|---|
| 1 | 0.5 | 2 | ✗ |
| 2 | 1.5 | 3 | ✗ |
| 3 | 2.5 | 4 | ✗ |
| … | … | … | ✗ |
| 7 | 6.5 | 8 → 夹到 7 | 碰巧对 |

即**前 6 列整体右移，第 6、7 列被夹成同一列**。改成一个字：`Math.round` → `Math.floor`。

### 改完之后，实测反而更差

```
星期 7/10 → 5/10
```

### 这是整个项目最有价值的一次发现

**数学上正确的修正，实测效果反而下降。**

原因：模型给的 `leftRatio / rightRatio` **系统性偏左约半列，但只偏一部分块**。
`round` 版本那次"多 +1"恰好补偿了这个偏差，所以分数更高。

> **结论：比例坐标这条路走到头了。** 不是公式错，而是**模型的输入有系统偏差**，
> 任何靠"修公式"去补偿的尝试都只是碰运气。

## 六、第 5 次：回到"模型判断" + 程序兜底 + 标记可疑（成功）

### 我的提问（原文摘录）

```
修识别的最后三件事。不要再用比例去算列，改成「模型判断 + 程序兜底 + 标记可疑」。
背景（实测）:
· 用 round 算列：星期 7/10；改成 Math.floor（数学上正确）：星期 5/10。
  原因：模型给的 leftRatio/rightRatio 系统性偏左约半列，且只偏一部分块；
  round 那个"多 +1"恰好补偿了它，所以反而更准。比例坐标不可靠。
· 节次：startSlot 普遍偏 1-2 行，跨度永远 1（模型数不出块占几行）。

【一】契约加回 colIndex 与 rowStart/rowEnd，比例仅作交叉校验
【二】lib/blocksToCourses.ts 改为「判断优先、兜底、标可疑」
1. col：优先用 colIndex；缺失才回退到 leftRatio；
   若 colIndex 与 ratio 推出的列相差 >= 2 列 —— 标 suspect，仍用 colIndex
2. 节次：rowEnd > rowStart 用模型跨度；
   若 rowEnd === rowStart（读不出高度）—— endSlot = startSlot + 1 并标 suspect
【四】前端校对表格标黄可疑行
```

### 实测（`eval/cases/final1.json`）

```
课程名匹配    10/10（100%）
星期准确率     9/10（ 90%）
节次跨度       8/10（ 80%）
地点准确率    10/10（100%）
平均时间误差   11.5 分钟
```

**只剩 3 处错，而且全部可解释：**

| 课程 | 错项 | 说明 |
|---|---|---|
| 网页设计 | 节 5-6 / 应 5-8 | 模型没看出跨 4 节 |
| 职业英语 | 周 3 / 应 4 | 列判错一格 |
| 程序设计基础 | 节 1-2 / 应 1-4 | 同样没看出跨 4 节 |

## 七、五代对比（这张表就是结论）

| 版本 | 契约 | 星期 | 节次跨度 | 时间误差 |
|---|---|---|---|---|
| 1 | 模型自己判断 day/slot | 2/10 | 1/10 | — |
| 2 | 网格 `columns/rows/cells` | 7/10 | 0/10 | — |
| 3 | 课程块 `blocks` | 7/10 | 0/10 | 40.5 分钟 |
| 4 | 比例坐标 + `Math.round` | 7/10 | 0/10 | 40.5 分钟 |
| 4' | 比例坐标 + `Math.floor`（数学修正） | **5/10** | 0/10 | 53 分钟 |

## 八、我的人工干预清单（这条链的核心价值）

1. **发现静默清零**：`cells` 长度不一致 → 10 门课全被丢弃，接口仍返回成功。
   改为"零结果返 422 + 不可自动修正的项计入 invalidCount 并提示"。
2. **发现"跨度全为 1 节"是假正常**：`endSlot < startSlot → endSlot = startSlot`
   会把"读不出高度"变成"看起来正常但短一截的课"，比报错更难发现。
   改为单独统计 `spanSuspect` 并在校对表标黄。
3. **数学修正导致效果下降**：`round → floor` 后星期从 7/10 掉到 5/10，
   由此反推出"模型比例有系统偏差"这一结论，最终放弃比例路线。
4. **恢复"模型判断"**：加回 `colIndex`，但**不再盲信** ——
   用比例做交叉校验，矛盾时标黄交给人。
5. **默认给课程 +1 节**：把节次跨度准确率从 0/10 直接提到 8/10，
   因为大学课程多为两节连上；读不出高度时按 2 节导入并标黄。

---

## 九、遗留与结论

**遗留**：3 门课的节次跨度仍不准（跨 4 节的课被读成 2 节）。
**处理**：不追求 100%。产品本就强制校对（识别结果不直接写入日程），
这三行会在校对表里被标黄，用户改一次即可。

**这条链最能说明的事**：

> 识别准确率不是靠"再试一次提示词"提上来的，而是靠
> **一份标准答案（`eval/timetable-groundtruth.json`）+ 一套固定口径的指标**
> 才把"改好了还是改坏了"变成可判断的事。
> 中间那次"数学修正反而更差"，如果没有指标，我会以为修对了。
