# 05 · 知识点大纲：把"学高数"变成 15 个可执行的点

> **一句话**：用户说的是「我要学习高数」，AI 直接排日程只能排出"复习高数"这种空泛任务；
> 中间的缺失环节是**知识点** —— 先知道要学什么，才谈得上怎么排。
> **完整对话**：`raw/对话导出-1-知识点大纲与提示修复.md` 第 2、3 轮

---

## 一、起点：日程上的任务名太虚

方案对比做完后，实测生成的日程长这样：

```
周三 19:00-21:00  复习高数
周五 19:00-20:30  复习高数
周六 09:00-11:00  复习高数
```

**三条都叫"复习高数"，用户拿着这个日程不知道今天该看哪一章。**

同时还有第二个问题：**可行性判断没有客观依据**。
`requiredHours` 是模型自己估的（实测估成 80 小时），而目标只是「期末高数考到 80 分」。

---

## 二、关键设计判断：知识点要放在"方案"之前

一开始的顺序是：目标 → 方案 → 日程。

改成：**目标 → 知识点大纲 → 方案 → 日程**。

理由很直接：

```
知识点清单给出了「到底有多少内容要学」—— 这是客观的
   15 个知识点 × 平均 118 分钟 = 1770 分钟 = 29.5 小时

有了这个数，"可行性"就不用模型猜了
   需求 29.5 小时 vs 可用 55 小时 → 可行
```

**一举两得**：可行性有了依据、日程标题变得具体。

---

## 三、我的提问（原文摘录）

```
新增「知识点大纲」接口：把一个目标拆成可执行的知识点清单。

为什么放在方案之前:
现在的可行性判断靠模型自己估「学高数需要 80 小时」，实测把
「每周10小时/5.5周」判成「不可行」。
改成先出知识点清单，总需求时长由程序把清单加出来，可行性就有客观依据。

【一】新增类型 KnowledgePoint
{ id, name, category, difficulty: "基础"|"进阶"|"难点", estimatedMinutes, order, mastered? }

【二】新增 app/api/syllabus/route.ts
POST { goal, syllabusText? }   // syllabusText 可选：用户粘贴的教材目录
返回 { ok, subject, points[], totalEstimatedMinutes, source, droppedCount }

提示词要点:
- 若 syllabusText 非空：必须以它为唯一来源拆分，不得添加它没有的内容
- 若为空：按主流教材与考纲给 8-15 个核心知识点，order 按学习依赖排序
- name 必须具体（「洛必达法则」可以，「导数」太笼统，应拆成「求导法则」「隐函数求导」）
- estimatedMinutes 在 30-240 之间
- 不要输出任何日期、时间点、任务安排

程序侧校验（不要信任模型）:
- points 数量 clamp 4..30；estimatedMinutes clamp 15..480
- name 为空的丢弃并计数
- order 一律按数组顺序重排为 1..n（忽略模型给的 order）
- totalEstimatedMinutes 由程序求和
```

**其中最关键的两条**：`order` 不信模型、`totalEstimatedMinutes` 由程序求和。
这两处一旦交给模型，数字就又会飘。

## 四、实测结果

输入目标「期末高数考到 80 分」，耗时 22.6 秒：

```
subject = 高等数学
15 个知识点 ｜ 1770 分钟 = 29.5 小时 ｜ 程序求和一致 ✓

 1. 导数的定义和几何意义        [基础]  60 分   第一章 函数、极限与导数
 2. 函数的连续性               [基础]  60 分   第一章
 3. 导数的计算方法             [进阶] 120 分   第一章
 4. 高阶导数                  [进阶]  90 分   第一章
 5. 隐函数求导                [难点] 150 分   第一章
 6. 导数的应用：单调性与极值     [难点] 120 分   第一章
 7. 微分中值定理和导数的应用     [难点] 180 分   第一章
 8. 一元函数的积分法            [基础]  90 分   第二章 不定积分
 9. 不定积分的计算方法          [进阶] 150 分   第二章
10. 定积分的概念与性质          [基础]  60 分   第二章
11. 定积分的计算方法            [进阶] 120 分   第二章
12. 定积分的应用                [难点] 180 分   第二章
13. 多元函数的微分法            [基础]  90 分   第三章 多元函数微分学
14. 多元函数的极值与条件极值      [进阶] 120 分   第三章
```

### 这份产出为什么算"合格"

| 检查点 | 结果 |
|---|---|
| 粒度 | 每个 60-180 分钟，都是"一次能学完一块"的量级 ✅ |
| 具体性 | 没有"导数"这种粗粒度，而是拆成"求导法则 / 隐函数求导 / 高阶导数" ✅ |
| 有章节 | `category` 落在第一、二、三章 ✅ |
| 有难度 | 基础 → 进阶 → 难点梯度合理 ✅ |
| 有顺序 | 从定义 → 计算 → 应用，符合学习依赖 ✅ |
| 数字自洽 | 15 条求和 = 1770 分钟，与接口返回值一致 ✅ |

## 五、它带来的两个连带收益

### ① 可行性判断终于有了依据

```
改之前：模型估「需要 80 小时」-> 判「不可行」（误判）
改之后：知识点加出来 29.5 小时 vs 可用 55 小时 -> 判「可行」
```

### ② 日程标题从"复习高数"变成具体知识点

`/api/goal` 的提示词加了约束：生成的任务标题必须能在选中知识点的 `name` 里找到匹配，
找不到的计入 `droppedCount`。于是日程变成：

```
周三 19:00-20:30   隐函数求导
周五 19:00-21:00   微分中值定理和导数的应用
周六 09:00-11:00   不定积分的计算方法
```

---

## 六、知识点从哪来：三种来源，以"AI 生成 + 人工可改"为主

我在设计时明确了一个前提：**不能假装 AI 一定懂你们学校的教学进度**。

| 来源 | 做法 | 本项目是否实现 |
|---|---|---|
| **A. AI 按主流教材生成** | 直接生成，界面标注「AI 按主流教材生成，可能与本校教学进度不同，请核对」 | ✅ 主路径 |
| **B. 用户粘贴教材目录/考纲** | 传 `syllabusText`，提示词要求"必须以它为唯一来源，不得添加" | ✅ 可选入口 |
| **C. 手动增删改** | 大纲面板里逐条可改名、改难度、改时长、删除、新增 | ✅ 默认能力 |

**A 主路径 + B/C 兜底** —— 因为「AI 给的大纲不准」是必然会发生的事，
产品必须让用户两分钟内改成自己要的，而不是要求 AI 一次给对。

---

## 七、人工干预小结

1. **决定知识点放在方案之前**：让"需求总时长"由清单加出来，取代模型瞎估。
2. **规定知识点粒度**：30-120 分钟能学完一块，并要求 name 具体到"洛必达法则"这一级。
3. **不信模型的两个字段**：`order` 按数组顺序重排、`totalEstimatedMinutes` 由程序求和。
4. **明确三种知识点来源**：AI 生成（主）+ 用户提供目录（可选）+ 手动编辑（兜底）。
5. **要求界面标注来源与不确定性**：「AI 按主流教材生成，请核对」这句话必须出现 ——
   不能让用户以为这是本校官方大纲。

---

## 八、这条链的结论

> **用户说"我要学习高数"时，缺的不是日程，是"要学什么"。**
>
> 直接跳到排日程，只会得到一堆叫"复习高数"的方块；
> 先在中间插一层「知识点」，日程才变成"今天学隐函数求导"，
> 而"需要多少小时"也才有客观答案。
>
> 这一层是产品从"日历 + 聊天框"变成"学习规划工具"的分水岭。
