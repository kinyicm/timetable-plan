# 02 · 手机照片一上传就 413：从开发日志里发现的真实失败

> **一句话**：这不是压测出来的问题，是**开发服务器日志里真实出现的 413** —— 用户第一次拍照就会撞上。
> **完整对话**：`raw/对话导出-2-全部开发轮次.md` 第 7 轮

---

## 一、触发事件：日志里的一条 413

第一阶段开发时，`next dev` 的日志里出现了这些行：

```
POST /api/recognize 400 in 84ms
POST /api/recognize 413 in 49ms
POST /api/recognize 400 in 6ms
```

`413` = Payload Too Large。当天 `/api/recognize` 的上限是我自己定的：
图片 base64 不超过 8 MB。

**算一下就知道这是必然的：**

| 图片 | JPEG 大小 | base64 后 |
|---|---|---|
| 12 MP 手机照 | 约 5.4 MB | 约 7.2 MB（贴着上限） |
| 48 MP 手机照 | 约 21.6 MB | 约 28.9 MB（直接拒绝） |

**结论：放宽上限解决不了。** 48 MP 的照片放大到 30 MB 也没意义，
视觉模型不会因为图片更大就更准，只会更慢更贵。

---

## 二、我的提问（原文）

```
在 app/components/ImportTimetable.tsx 里加客户端压缩，修复大图被 413 拒绝。

现状：选图后用 FileReader 读成 base64 直接 POST 到 /api/recognize。
问题：手机照片 4-6 MB，base64 后超 7 MB，服务端上限 8 MB，实测已出现 413。

要求：
1. 新建 lib/image.ts，导出
   compressImage(file: File): Promise<{ base64: string; mimeType: string; width: number; height: number }>
   - 用 createImageBitmap(file) 读图，失败回退 new Image() + URL.createObjectURL
   - 长边 >1600px 时等比缩到长边 1600px
   - canvas.toBlob(..., "image/jpeg", 0.82) 输出
   - Blob 转 base64（不含 data: 前缀，mimeType 单独返回）
   - 原图长边 ≤1600 且文件 ≤1.5 MB 时复用原文件，避免无谓重编码
2. ImportTimetable.tsx 改用它，状态文案「正在压缩…」→「正在识别…」
3. 压缩后若 base64 仍 >7 MB，前端提示「图片太大，请重新拍摄或裁剪」，不发请求
4. 不要改 app/api/recognize/route.ts

约束：不要引入新依赖。
```

**几个刻意的设计决定**（都写进了 Prompt，不让 AI 自由发挥）：

| 决定 | 理由 |
|---|---|
| **必须在客户端压缩** | 服务端收到时已经太晚了；而且客户端压缩还能省上传流量 |
| **长边 1600px / JPEG 0.82** | 课表是文字图，1600px 足够辨认；再大对识别没有帮助 |
| **小图跳过重编码** | 原图够小时重编码只会损失质量、浪费时间 |
| **压缩后仍超限就在前端拦下** | 不要发出一个"必然失败"的请求，让用户等 8 秒再看错误 |

## 三、AI 的产出

新增 `lib/image.ts`（113 行）：

- `createImageBitmap` 读图，失败回退 `new Image() + URL.createObjectURL`
- 等比缩放到长边 1600px，`canvas.toBlob` 输出 JPEG 0.82
- Blob → base64（不含 `data:` 前缀）
- **正确释放资源**：`bitmap.close()` / `URL.revokeObjectURL()`
- 小图分支直接复用原文件

`ImportTimetable.tsx` 改为两段状态文案：「正在压缩…」→「正在识别…」。

## 六、人工干预小结

1. **定位方向**：不是"调大上限"，而是"在客户端就把图变小"。放宽上限只会把问题推迟到 48 MP 照片。
2. **明确写出实现细节**：`createImageBitmap` + ObjectURL 回退路径、缩放阈值、质量参数 —— 这些都写在 Prompt 里，避免 AI 自己发明参数。
3. **要求释放资源**：图片处理最容易漏的是 `ImageBitmap.close()` 和 `revokeObjectURL`，一张图不释放就是一个内存泄漏。
4. **要求在压缩后仍超限时前端拦截**：体验上，快速失败优于慢速失败。
