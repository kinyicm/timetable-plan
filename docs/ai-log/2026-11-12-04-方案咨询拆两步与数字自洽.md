# 04 · 从"直接排事件"到"先给三个方案"：拆两步，并把数字拿回程序

> **一句话**：AI 一次吐完所有事件时，用户没有选择权、目标大时还会超时；
> 改成「先给方案（轻）→ 选定后再排（重）」，并把方案的数字从模型手里拿走。
> **完整对话**：`raw/对话导出-2-全部开发轮次.md` 第 31、36、37 轮

---

## 一、起点：一次吐完事件的三个问题

第一版 `/api/goal`：给目标 + 空闲时段，直接返回一堆事件。

实测（目标「期末高数考到 80 分 / 每周 10 小时」）：

```
模型返回 21 条安排
  -> 7 条越界被吸附到最近空档
  -> 8 条放不下被丢弃
  -> 只剩 6 条
耗时 39 秒
每个任务 2-3.7 小时（要求是 30-120 分钟）
```

再把目标改成「一个月内学完三门专业课 / 每周 30 小时」：

```
HTTP 500 -- 规划超时
```

### 三个问题

| 问题 | 后果 |
|---|---|
| **用户没有选择权** | 要么全接受、要么全拒绝；AI 怎么排就怎么排 |
| **越界率 80%** | 模型自己算"这个时间在不在空档里"，算不准 |
| **目标一大就超时** | 事件数量膨胀 → 调用超时 → 「AI 说不出方案」这条路径直接断 |

---

## 二、第一步改动：拆成"方案咨询"与"事件生成"两段

### 我的提问（原文摘录）

```
新增「方案咨询」接口：给目标，返回可行性判断与 2-3 个候选方案（只出思路，不出事件）。

为什么拆成两步：
现在的 /api/goal 一次生成全部事件，用户只能全接受或全拒绝；
且目标大时事件多，实测「每周30小时」直接超时 500。
拆成「先出方案（轻）→ 选定后再出事件（重）」既给了用户选择权，也不会超时。

【一】新建 app/api/advise/route.ts
POST { goal: {title, deadline, hoursPerWeek, priority},
       context: { today, freeHoursThisWeek, weeksUntilDeadline, existingTitles } }
返回 {
  feasibility: { verdict, requiredHours, supplyHours, gapHours, note },
  options: [{ id, name, strategy, summary, sessionsPerWeek, avgSessionMin,
              totalHours, pros[], cons[], risk }],
  recommendation, recommendReason
}
提示词要点：
- 必须给 3 个方案，strategy 尽量不同：
  daily 分散式 / weekly 集中式 / sprint 冲刺式
- 每个方案的节奏数字要自洽
- 不要输出任何事件、时间点、日期 —— 这一轮只出方案
- actions 字段一个都不要有
```

### 三个方案的"科学依据"（写进提示词的三档，不是我编的）

| 策略 | 节奏 | 优点 | 代价 |
|---|---|---|---|
| `daily` 分散式 | 每天 30-60 分钟 | 记忆最牢、易成习惯 | 要求每天坚持 |
| `weekly` 集中式 | 每周 2-3 次，每次 90-120 分钟 | 单次深入、适合攻坚 | 间隔长易遗忘 |
| `sprint` 冲刺式 | 前段打基础、后段高强度 | 前期压力小 | 后期风险高 |

**这三档来自学习节奏的常识权衡，AI 的任务是把它们写清楚，而不是发明数字。**

---

## 三、实测：框架对了，但数字全是编的

`/api/advise` 跑通后，实测两个用例：

**用例 A：期末高数 80 分 / 每周 10 小时 / 5.5 周**

```
可行性判成「不可行」：需要 80 小时 ｜ 可用 55 小时
     ↑ 模型自己估"学高数要 80 小时"，没有依据
方案A：每周 7 次 × 120 分钟 = 14 小时/周
     ↑ 用户填的是 10 小时/周，超了 40%
totalHours 77 小时   （而 10 × 5.5 = 55）
```

**用例 B：一个月学完三门课 / 每周 30 小时**

```
方案A：每周 7 次 × 30 分钟 = 3.5 小时/周
     ↑ 用户填 30 小时，只给了 11%
totalHours 14 小时   （差一个数量级）
```

### 诊断

```
sessionsPerWeek × avgSessionMin × weeks 与用户填的 hoursPerWeek 完全没有关系。
评委一眼就能看出"AI 在编数字"。
```

## 四、第二步改动：数字由程序算，模型只写文字

### 我的提问（原文摘录）

```
重写 /api/advise：所有数字由程序算，模型只负责文字。

问题（实测）:
1. 可行性判断错：模型自己估「需要 80 小时」——这个数没有依据。
2. 方案数字与用户填的 hoursPerWeek 完全无关。

【一】可行性完全由程序算（不再问模型「需要多少小时」）
定义：
  H = goal.hoursPerWeek；W = weeksUntilDeadline
  weeklyCapacity = context.freeHoursThisWeek
  demandHours   = H * W
  capacityHours = weeklyCapacity * W
  gapHours      = capacityHours - demandHours
判定：
  · H > weeklyCapacity               -> "不可行"
  · demandHours > capacityHours*0.8  -> "紧张"
  · 其余                              -> "可行"

【二】三档节奏由程序生成
  A daily  : sessionsPerWeek = 7, avgSessionMin = roundTo15(H*60/7)
  B weekly : sessionsPerWeek = 3, avgSessionMin = roundTo15(H*60/3)
  C sprint : sessionsPerWeek = 4, avgSessionMin = roundTo15(H*60/4)
  totalHours = round(H * W * 10) / 10

【三】模型只产出文字
把算好的数字作为「既定事实」放进提示词，要求模型只输出
{ options:[{id,name,summary,pros,cons,risk}], recommendation, recommendReason }
明确禁止模型输出或修改任何数字。

【四】服务端合并：数字用程序的，文字用模型的，按 id 对齐
```

### 关键设计：可行性到底在判断什么？

**改之前**：猜"学高数需要多少小时" —— 没人知道，模型也是瞎猜。

**改之后**：

> **你承诺每周投入 H 小时，你的课表容得下吗？**

这个问题 100% 由程序算得出来，而且这才是学生真正会问的问题。

## 五、实测（修正后）

**用例 A：期末高数 80 分 / 每周 10 小时 / 5.5 周 / 本周空档 26 小时**

```
可行性：可行（需求 29.5 小时 vs 可用 55 小时，余量 25.5 小时）
  ↑ 需求 29.5 小时来自"知识点大纲"的总时长，不再是模型瞎估

方案 A：每周 7 次 × 90 分 = 10.5 h/周   偏差 5%  ✓
方案 B：每周 3 次 × 200 分 = 10.0 h/周  偏差 0%  ✓
方案 C：每周 4 次 × 150 分 = 10.0 h/周  偏差 0%  ✓
（用户填的每周 10 小时）
```

**用例 B：每周 30 小时 / 4 周 / 本周空档 26 小时**

```
H = 30 > weeklyCapacity = 26  ->  verdict = "不可行"
note：「你计划每周投入 30 小时，但按课表本周只剩 26 小时空档」
```

## 六、人工干预小结

1. **把"一次吐完"拆成"方案 → 选定 → 排事件"**：解决"用户没有选择权"和"目标大时超时"两个问题。
2. **给三个方案定了三种学习节奏**：不是我让模型随便编，而是指定 `daily/weekly/sprint` 三种策略，让它只负责把取舍讲清楚。
3. **把可行性判断的定义改对了**：从"猜需要多少小时"改成"你承诺的小时数课表装不装得下"。
4. **把数字全部拿回程序**：`sessionsPerWeek / avgSessionMin / totalHours / requiredHours` 全部由代码算，模型只写文字。
5. **禁止模型输出数字**：Prompt 里明确写"不许出现这些字段"，并在服务端合并时按 id 对齐、忽略模型给的一切数字。

---

## 七、这条链的通用结论

> **"让 AI 做规划"不等于"让 AI 报数字"。**
>
> 一个可用的规划功能需要三层分工：
> **程序算硬约束**（可用空档、需求总时长、可行性）→
> **模型做权衡与表达**（三种节奏的取舍、风险、推荐理由）→
> **用户做决策**（选哪个方案）。
>
> 少任何一层都会出问题：缺第一层，数字是编的；缺第二层，只有一堆事件没有理由；缺第三层，用户被 AI 绑架。
